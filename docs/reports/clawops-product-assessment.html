摘要 · 五点结论

1. 产品定位清晰且克制。ClawOps 不是通用聊天机器人，而是一个面向 20~50 人团队值班与运维场景的常驻式诊断 Agent 平台，以 Web 控制台为主、IM 机器人与 CLI 为辅，且明确定义了不做什么（无多租户 SaaS、无 K8s 编排、无本地推理）。这种边界清晰度在同类个人/小团队作品中属少见。

2. 核心价值在于"闭环"而非"问答"。其差异点不是让模型更会说，而是让模型能查、能判、能停、能续、能留痕——查真实指标与日志、给出带置信度的根因、高危动作强制人工审批、结论回写工单并沉淀为知识。这恰好对应信息系统运营优化中最耗人力的"关联分析"环节。

3. 架构边界被做成可执行的机器断言。最有新意的工程决策是：把"内核与 AI 框架解耦"这一通常只写在文档里的约定，落成了 ArchUnit 测试 + CI 门禁（harness 禁依赖兄弟模块与 HTTP 客户端；LangChain4j 类型禁入 public API）。框架因此可替换，内核因此可独立测试。

4. 关键技术风险已识别并给出机制级解法。包括：HITL 暂停后恢复破坏消息配对（解法：trim 尾部未配对 toolCalls + 按参数匹配放行）、长任务进程重启即失（解法：每步 Checkpoint + 跨进程续跑）、工具失败拖垮整体（解法：三阶防护降级）、中文全文检索失效（解法：CJK bigram 分词）。

5. 最重要的采购提示：量化验证尚未开始。截至本报告日，项目仅有一项实测数据（上下文压缩 1697→512 token），优化前后的业务指标（根因命中率、MTTR、人力节省）均为机制推断，尚无实测。评测集与靶场计划在 W3~W4 落地。本报告 §4 所有数字均已标注证据等级，请勿视作实测承诺。

§1

这个产品是什么，定位是什么

一句话概括：把一位「会查、会判、会请示、会留档」的资深值班工程师，做成了一个可自托管、可审计、可量化的软件系统。

1.1 定位陈述

ClawOps 是一个面向 20~50 人规模团队值班 / 运维（DevOps）场景的自托管常驻 Agent 平台。它的目标不是替代人，而是在信息系统出问题时，自动完成最耗时、最依赖经验的「信息收集 → 关联分析 → 根因假设」链条，并把最终决策权在受控的前提下交回给人。

出处：docs/TASK_BOOK.md §1 已确认

1.2 产品形态与用户角色

产品形态

Web 控制台（主）+ IM 机器人（副，W3）+ CLI（副，W3）。
明确不做：C 端通用对话、编码 CLI、桌面助手。

主要角色

值班 / 运维工程师（主力使用者）
团队负责人 / 管理员（配置与审计）
普通同事（知识问答）

部署形态

Docker Compose 一键起停，自托管于企业自有服务器；数据不出内网。

§2

怎么优化某个信息系统的运营

本节回答两个问题：它在系统里到底怎么运转（2.2 运作原理），以及接进一个陌生系统要多少成本（2.3 接入机制）。

为了让非 DevOps 背景的评审快速进入，下表给出术语对照。后续章节将交替使用两侧表述。

ClawOps / 运维原术语仓储物流系统对应物说明
服务（service）库存服务 / 订单服务 / 分拣调度服务被监控的最小单元
告警（alert）出库单积压告警 / 分拣线停线告警闭环的起点

2.2 运作原理：一次故障处理的四阶段闭环

传统信息系统运营的痛点在于：数据分散在不同系统里，而"把数据关联起来形成判断"这件事只能靠人。指标在监控平台、日志在日志系统、变更记录在发布平台、历史经验在老员工的记忆或散落的文档中。一次故障中，工程师有 60%~75% 的时间花在"找数据"和"拼数据"上，真正的决策时间很短。

ClawOps 的运作原理，本质上是把这条"找数据 → 拼数据 → 形成假设 → 验证假设"的链条自动化：

感知 分层上下文组装

按 System → 角色 → 工具说明 → 记忆 → 当前任务 五层组装 Prompt，并对 token 计数。达到阈值（默认 80%）触发窗口压缩，保留目标与关键事实，丢弃陈旧历史。已确认

推理 模型决策与工具选择

模型在每轮输出「文本作答」或「工具调用」之一。工具定义以 JSON Schema 形式提供，参数由框架侧生成描述。已确认

行动 三阶防护后执行

参数 Schema 校验 → 超时隔离 + 指数退避重试（≤3 次）→ 熔断 / 降级 / 转人工。同时有步数上限、时长上限与重复动作检测三重防死循环。已确认

反馈 落库与闭环回写

工具入参出参摘要写入 task_step，上下文快照写入 task.context_messages，动作写入 audit_log；最终结论回写工单。回写层尚未实现 未落地

2.3 如何接入不同的信息系统

这是本项目在架构上最值得关注的部分。它用三层解耦来回答"怎么完美接入不同系统"这个问题。

① 五类标准接口抽象

Connector 层把异构系统归一为五类能力：Metrics / Log / Ticket / CMDB / Change。任何系统只要能提供其中任一类数据，即可被 Agent 使用。 已确认

② 注解式工具注册

新增工具只需在方法上加 @Tool(name, description, permission) 与 @ToolParam，框架自动完成 JSON Schema 生成、参数校验与权限绑定。已确认

③ MCP 标准协议

规划通过 MCP Client 接入符合 Model Context Protocol 的外部工具，使接入从"写代码"降级为"配服务"。未落地

接入的安全梯度：先只读，后写入

对一个真实企业系统，"接入"最大的阻力不是技术而是风险。ClawOps 用权限分级把接入拆成可渐进推进的梯度：

权限等级典型工具执行策略接入风险
READmetrics.query、log.search、knowledge.search自动执行极低 · 建议首批接入
WRITEticket.create、ticket.comment需 HITL 审批中 · 建议第二批
DANGEROUSservice.restart、deploy.rollback、config.change强制审批 + 审计留痕高 · 最后接入或不开

注：当前代码库已落地 metrics.query（Prometheus 真实实现）与 log.search（Mock 实现，可注入 ERROR）；knowledge.search 属 W2 待办 E6；Ticket / CMDB / Change 三类接口属 W3 计划。已确认

✓ 对采购最有价值的一点

接入成本与风险被结构化地分层了：企业可以只做第一步（只读接入指标与日志），就已经能获得"自动关联分析"的主要收益，而无需开放任何写权限。这大幅降低了 POC 的准入门槛与内部审批阻力。

3.2 创新点：问题 → 做法 → 价值

以下七项按「工程新颖度 × 对采购方的实际价值」排序。每项均标注落地状态。

创新 ①　架构边界的机器化校验 已确认

问题　Agent 内核一旦与 AI 框架（LangChain4j / Spring AI）耦合，内核就无法独立测试，框架也无法替换。

做法　harness 禁依赖兄弟模块、spring-web、servlet、任何 HTTP 客户端；LangChain4j 类型禁入 harness / orchestrator 的 public API 签名。关键在最后一步：这些约定不是写进文档，而是落成 ArchUnit 测试，违反即 CI 失败。

价值　框架可替换（任务书已备 Spring AI 2.0 备选）；内核可无 AI 依赖地做 TDD。对企业意味着技术栈锁死风险显著降低。

创新 ②　审批暂停—恢复语义 已确认

问题　主流 Agent 框架在「人工审批」处暂停后恢复时，容易破坏 LLM 消息配对约束（assistant 的 tool_call 必须有对应 tool result），导致续跑失败。

做法　① 暂停前 trimUnresolvedToolCalls() 裁掉尾部未配对的 assistant(toolCalls) 消息；② 恢复时从快照重建 history，模型重新发起调用；③ ApprovedCallGate 按 (taskId, toolName, arguments) 匹配已批准的审批单放行。整条语义记入 ADR-008。

价值　这是把"人机协同"从演示级做成工程级的关键一环——高危动作可安全地中断、审阅、恢复。

创新 ③　每步 Checkpoint + 跨进程断点续跑 已确认

问题　长时间诊断任务一旦进程重启，上下文与进度全丢。

做法　每个工具步的入参 / 出参摘要落 task_step，上下文快照落 task.context_messages；TaskResumeIT 集成测试模拟「阶段一跑到高危动作暂停 → 丢弃 runner 实例（模拟进程死亡）→ 阶段二新建实例 → resume → 断言续跑成功且步骤全序」。

价值　运维场景常有长任务与不稳定环境，断点续跑是可用性刚需；且已有集成测试证据，非口头承诺。

创新 ④　工具执行三阶防护 + 三重防死循环 已确认

问题　工具调用是 Agent 系统最脆弱的一环：参数错、超时、下游雪崩、模型陷入循环调用。

做法　三阶防护 = 参数 Schema 校验 → 超时隔离 + 指数退避重试（≤3 次，baseDelay 500ms）→ 熔断（5 次失败 / 30s 窗口，10s 半开）/ 降级 / 转人工。防循环 = 步数上限 10 + 时长上限 60s + 重复动作检测（同一「工具名 + 规范化参数」连续出现 2 次即终止）。

价值　降级而非崩溃——工具失败返回 degraded 结果，Agent 继续推理。这是自动化的信任基础。

创新 ⑤　错误码携带 Agent 语义 已确认

问题　普通错误码只描述"出了什么错"，无法指导系统"接下来怎么办"。

做法　error-codes.yaml 作为单一事实源，除 code / name / http 外，还定义 retryable 与 degradeAction（可重试 / 降级换路径 / 转人工）。前端、CLI、Agent 三阶防护共用此文件，禁止各处硬编码。已定义 1xxx 通用 / 2xxx 任务域 / 3xxx 工具执行 / 4xxx RAG / 5xxx 集成 / 9xxx 系统内部，一经发布只增不改不复用。

价值　降级策略从"散落在各处的 if-else"变成可集中治理的声明式配置，运维可审计、可调整。

创新 ⑥　中文友好的混合检索 + 引用溯源 已确认

问题　① PG 的 simple 分析器不支持中文，全文检索对中文语料基本失效；② RAG 回答不可溯源则无法在运维场景被信任。

做法　向量侧用 pgvector + HNSW（vector_cosine_ops）；全文侧在应用层做 CJK bigram 分词（连续汉字两两滑动成 bigram，拉丁词原样小写保留）后写入 tsvector 列 + GIN 索引；两路召回在应用层用 RRF 融合（score = Σ 1/(k+rank)，k=60），命中来源标记为 vector / fulltext / hybrid。RetrievedChunk 携带 docTitle / seq / content，支持前端引用跳转。

价值　解决了中文企业知识库 RAG 的两个真实痛点（检索失效 + 无法溯源），且不引入额外的搜索引擎组件。

创新 ⑦　Fake-First 的确定性测试策略 已确认

问题　Agent 系统难以测试：依赖 LLM、结果不确定、测试成本高。

做法　自研可编程 FakeChatModel（按轮次弹出预设回复、记录全部入参供断言、支持注入 token usage）；单测与集成测试一律 Fake，禁止真实 API；真实 LLM 调用仅允许出现在 E2E 评测、手动验证脚本与 CI 冒烟子集（≤5 条）。测试金字塔 ≈ 70% 单测 / 25% 集成 / 5% 评测，覆盖率门槛由 Jacoco 强制，只升不降。

价值　让一个 AI 系统具备可回归、可 CI 门禁、成本可控的工程属性。对采购方是可验证的质量保证。

另：极低的运行门槛 已确认

2 vCPU / 4 GiB 单台服务器 + 2 GiB swap 即可运行，逐项内存预算：主应用 512M、PG 300M、Prometheus 300M、靶场 2×128M、Mock 128M、Redis 128M、Nginx 20M、系统预留 ~1G。模型与向量全部走外部 API，月度成本上限设定为 ≤ ¥100，CLI 侧做调用计数与熔断。对中小企业意味着硬件与许可成本几乎可忽略。

3.3 新颖度分级：哪些是"真创新"，哪些是"合理工程"

项新颖度评审意见
审批暂停—恢复语义高解决了 HITL 恢复期的消息配对这一真实工程难题，且有明确的 ADR 与集成测试佐证。
架构边界机器化校验高把"原则"变成"可执行断言"，是可复制的工程方法论；对降低框架锁定风险有实际价值。
CJK bigram + RRF 混合检索中技术本身是成熟方案的组合，但组合方式与"不引入额外组件"的取舍是合理的工程判断。
每步 Checkpoint / 断点续跑中思路通用，落地的完整度（含跨进程 IT 验证）值得肯定。
错误码携带 Agent 语义中把降级策略声明化、集中治理，是好的工程实践，非算法创新。
三阶防护 / 防死循环工程基线属生产级 Agent 系统应有能力，做得扎实但不算新颖。

§5

产品整体运作流程（Pipeline）

从一条告警进入系统，到结论回写工单并被纳入评测，共 8 个阶段。标注了每阶段的数据落点与防护机制。

1

事件接入 Webhook / IM / Cron

告警 Webhook、IM 消息或定时巡检任务进入系统。Webhook 侧做签名校验与消息去重，避免同一故障重复触发诊断任务。

2

任务创建与落库 task 表 · CREATED

通过 TaskStore 创建任务记录并落 PostgreSQL，状态置为 CREATED。任务从这一刻起具备持久化身份，后续任何中断都可恢复。

3

上下文组装 ContextManager

按 System → 角色 → 工具描述 → 记忆 → 当前任务 五层组装，并做 token 计数。达到阈值（默认 80%）触发窗口压缩：保留目标与关键事实，丢弃陈旧历史并插入摘要占位。

4

模型推理与工具决策 ModelClient

模型每轮输出「文本作答」或「工具调用」。工具以 JSON Schema 描述，LangChain4j 类型被隔离在 gateway 适配器内部，不进入内核 public API。

5

工具执行三阶防护 校验 → 重试 → 熔断

参数 Schema 校验 → 超时隔离 + 指数退避重试（≤3 次）→ 熔断（5 次 / 30s，半开 10s）/ 降级 / 转人工。并行三重防死循环：步数上限 10、时长上限 60s、重复动作检测（连续 2 次即终止）。

6

审批闸门（HITL）approval 表 · PAUSED

执行前询问 ApprovalGate。命中 DANGEROUS 则创建审批单、任务转 PAUSED_FOR_APPROVAL，并裁剪尾部未配对的 assistant(toolCalls) 消息。人决策后：批准 → 按 (taskId, toolName, arguments) 匹配放行并续跑；驳回 → 任务终止且工具不执行。

7

结果落库与审计 task_step / audit_log

每步工具入参出参摘要写 task_step（含 seq 全序），上下文快照写 task.context_messages，动作写 audit_log（actor / action / detail jsonb）。全流程可回放。

8

闭环回写与评测反馈 工单 / 知识库 / eval

结论回写工单系统并沉淀进知识库；评测脚本统计命中率、轮数、Token、时延分位，结果回流为下一轮优化依据。此段目前尚未实现。

5.1 阶段 3–6 的内部循环（Agent 迭代细节）

阶段 3 到阶段 6 并非线性执行，而是一个感知—推理—行动—反馈的迭代环，直到模型输出纯文本作答，或触及步数 / 时长 / 循环上限：

迭代终止条件（三选一）

① 模型输出纯文本 → SUCCEEDED
② 步数 ≥ 10 或耗时 ≥ 60s → MAX_STEPS / TIMEOUT
③ 同一「工具名 + 参数」连续出现 2 次 → LOOP_DETECTED

异常出口

需审批 → PAUSED_FOR_APPROVAL（可恢复）
工具失败 → 三阶防护降级后继续
未捕获异常 → ERROR + 审计留痕

7.2 主要风险与缓释

风险 1　收益未经验证

缓释　以「只读接入 + 人工复核」方式做 2~4 周 POC，用本企业真实告警样本对比人工基线，自行产出 ROI 数据。项目已备好评测框架（eval_case 表 + eval run 命令），可直接复用。

风险 2　接口层与前端尚未完成

缓释　后端核心（持久化 / 断点续跑 / 审批 / RAG）已就绪且有测试覆盖；剩余为 REST 暴露与页面，属确定性工作量，可评估排期后再决策。

风险 3　单人项目的人员依赖

缓释　项目以「规约驱动」弥补：ADR 决策记录、ArchUnit 机器化架构校验、覆盖率门禁、OpenAPI 契约 diff、AI 生成留档（docs/ai-log/）。这些机制显著降低了新人接手的认知成本。

风险 4　模型 API 的外部依赖

缓释　适配器隔离 + 双轨装配（有 key 走 OpenAI 兼容接口，无 key 走 Fake），切换模型供应商不触及内核；成本侧有调用计数与配额熔断。

7.3 建议的推进路径

①

先问一个问题：要的是"产品"还是"架构参考"？

若需要可直接采购的成熟产品，ClawOps 目前不满足——它是作品集项目，无 SLA、无客户案例。若需要一套经过工程验证的 Agent 平台架构作为自研或二次开发的起点，它的完成度与规约严谨度相当有价值。

②

用只读接入做低成本 POC

只接指标与日志两类只读数据源，不开放任何写权限。此时已能验证核心价值：Agent 能否正确关联多源数据并给出可用根因。门槛低、内部审批阻力小。

③

补齐接口层并接入本企业系统

完成 E3–E6 的 REST 与工具封装，按 Connector 接口实现本企业的指标 / 日志 / 工单适配器。这部分是标准的 Spring 开发工作，风险可控。

④

用本企业样本产出实测报告

复用 eval_case 表与 eval run，灌入本企业真实故障样本与 ground truth，产出属于本企业的根因命中率、轮数、Token、时延分位数据——这才是能支撑采购决策的数字。

✓ 总结陈词

ClawOps 是一个架构判断成熟、工程纪律严格的 Agent 平台：它把「人机协同」「断点续跑」「降级不崩溃」「可审计」这些运维场景的刚需做成了机制，并用 CI 门禁把架构原则固化下来，这一点比多数同类项目更扎实。

但它尚未跨越从"机制建成"到"效果验证"的鸿沟。对采购方而言，合理的姿态是：认可其架构价值，但坚持用本企业的样本跑出属于本企业的数字，再决定是否投入。

AgentLoop感知—推理—行动—反馈的迭代循环，含步数与时长上限
HITLHuman-in-the-Loop，人工介入；本项目指高危动作的强制审批闸门
Checkpoint每一步工具调用的入参出参摘要与上下文快照，用于断点恢复与审计回放
RAG检索增强生成：先检索知识库片段，再让模型基于片段作答
RRF倒数排名融合，本项目用于合并向量检索与全文检索两路结果
CJK bigram中文分词方案：连续汉字两两滑动成词组，解决 PG simple 分析器不支持中文的问题
pgvector / HNSWPostgreSQL 向量扩展与近似最近邻索引，本项目用余弦距离算子
Connector外部信息系统适配层，抽象为 Metrics / Log / Ticket / CMDB / Change 五类接口
MCPModel Context Protocol，模型上下文协议，用于标准化接入外部工具（W3 计划）
ADRArchitecture Decision Record，架构决策记录；本项目要求任何偏离任务书的决定先记 ADR 再改代码
靶场 / Testbed用于评测的可控故障环境：模拟业务服务 + Mock 运维系统 + 故障注入脚本（W3）
